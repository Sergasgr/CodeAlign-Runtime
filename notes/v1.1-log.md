# CodeAlign-Runtime v1.1 — performance log

Branch `perf/v1.1`, following IMPLEMENTATION_PLAN.md §2. One entry per step: what changed, the measurements
(clean commit, `git_dirty: false`) and what they say. Final numbers for the README are re-measured at release (§2.5).

**Setup for every measurement:** RTX 5070 Ti (sm_120, 70 SMs, 48 MB L2, 896 GB/s), driver 595.91.07,
torch 2.13.0+cu130, CUDA 13. No other GPU clients (see the step 1 caveat: without host syncs the GPU never idles,
and a desktop or browser on the same GPU preempts kernels).

## Step 2 — §2.2 batched GQA attention, two launches per layer (commit 773fd65)

New `src/ops/gqa_attention.{h,cu}`: one partial launch over (KV chunks × KV heads × tokens) + one final launch.
A block reads each K/V row once for the 7 query heads of its group; its 4 warps take different positions with an
online softmax per head in registers; chunk size adapts to the context (≥ 32 positions, ≤ 32 chunks). The v1.0
Flash-Decoding kernels stay in the repo as the LEGACY v1.0 baseline (compiled into the kernels module only).

| Metric | Step 1 | Step 2 | × |
|---|---:|---:|---:|
| Block p50, S=128 / 512 / 2048 | 0.99 / 1.82 / 1.82 ms | 0.135 / 0.135 / 0.139 ms | 7.3 / 13.5 / 13.1 |
| Model p50, S=128 / 512 / 2048 | 27.07 / 49.65 / 49.66 ms | 4.09 / 4.11 / 4.20 ms | 6.6 / 12.1 / 11.8 |
| e2e TTFT / TPOT p50 | 287.7 / 25.1 ms | 28.7 / 4.10 ms | 10.0 / 6.1 |
| Kernel launches per decode step | 1,114 | 490 | |
| CUDA buffers (cudaMalloc) | 87.96 MiB | 97.69 MiB | +1.26 MB scratch per layer |
| PLD: cost of a 5.3-token verify vs a 1-token forward | 4.75× (v1.0) | 1.49× | |
| PLD overall speedup, identical output | 1.00× (v1.0) | 1.94× | |

- The block now grows with S (0.135 → 0.139 ms), as expected once attention is bound by the KV it reads.
- In-engine attention cost (from the step 3 profile, attention code unchanged): partial 5.0 µs + final 1.3 µs per
  layer at S=512 (16 chunks × 2 KV heads = 32 blocks); 4.4 + 1.1 µs at S=128. v1.0: ~1.9 ms per layer.
- Level 4, single head, same run (measured with step 3, cc04988): v1.1 kernel vs LEGACY v1.0 kernel 5.7–6.0× for
  S ≤ 16k, 4.2× at 65k, 2.5× at 131k, 1.6× at 262k; vs PyTorch 4.3× → 1.5×. Up to 16k the ~23 µs is host
  overhead of the binding call (allocations + 2 launches), not kernel time. At 65k the KV (33.5 MB) fits in L2, so
  33.6 µs beats the DRAM "ceiling"; from 131k it comes from DRAM: 99 µs (75% of 896 GB/s) and 182 µs (83%).
- Level 4, Qwen layer (14/2 heads): 20.5–21.2 µs per call (30.6 µs at T=6, S=2048) vs SDPA 166–198 µs (6.4–9.4×);
  same host-overhead caveat (the kernels themselves take ~6 µs, see above).
- PLD caveat for the README: the largest speedups come from degenerate, repetitive outputs (`def restock` ×15, one
  sentence ×25) that PLD copies; `cpp_getters` (1.18×) is the realistic case.

## Step 3 — §2.3 INT4 GEMV v2 (commit cc04988)

`gemv_int4_v2_kernel` (v1.0 kernel kept as the reference row): x staged in shared memory as two float4 arrays
(conflict-free), persistent grid (4 blocks × 8 warps per SM), 2 rows per warp as one contiguous span (no idle
lanes on 896-wide rows; 1 row when cols ≥ 2048), 8 word loads in flight per lane, nibble → float without I2F
(`(w ^ 0x88888888)`, `0x4B000000 | n`), optional bias in the epilogue (q/k/v bias launches removed).

**Levels 1–3 harness** (`./build/gemv_benchmark`, validation 30/30: 5 shapes × 6 kernels incl. v2 + bias):

| Shape | Kernel | L2-hot p50 | L2-cold p50 | Cold GB/s (% of 896) |
|---|---|---:|---:|---:|
| up/gate 4864×896 (2.3 MB INT4) | INT4 v1.0 | 25.7 µs | 26.4 µs | 89 (9.9%) |
| | INT4 v2 | 5.1 µs | 7.9 µs | 295 (33.0%) |
| | fp32 optimized (17.5 MB) | 9.3 µs | 28.4 µs | 614 (68.6%) |
| lm_head 151,936×896 (72.9 MB INT4) | INT4 v1.0 | 702.6 µs | 702.1 µs | 104 (11.6%) |
| | INT4 v2 | 95.0 µs | 110.2 µs | 662 (73.9%) |
| | fp32 optimized (545 MB) | 643.1 µs | 682.8 µs | 798 (89.1%) |

- lm_head: v2 is 6.4× faster than v1.0 and 6.2× faster than fp32 (byte ratio 7.5×): INT4 finally turns its byte
  reduction into speed (v1.0: 1.09×). §2.3 criterion (cold % of ceiling in the class of fp32 optimized) met.
- up/gate (2.3 MB) is launch/latency-bound: 33% of bandwidth cold is the ceiling of a single small GEMV.
- Nsight Compute, lm_head inside the engine: 105 µs, DRAM 80% of peak (716 GB/s), 0.2% excess shared-memory
  wavefronts (the split x layout is conflict-free), occupancy 64% (register-limited: 64 regs → 4 blocks/SM), top
  stall = waiting for loads (L1TEX scoreboard). Remaining headroom: ~10% (fewer registers → more warps in flight).

**Engine:**

- References on the same GPU: PyTorch eager 14.61 ms → the engine is 8.4× faster; llama.cpp Q4_0 1.33 ms → the
  engine is 1.30× slower.
- Profile (S=512, NVTX sections on), kernel time 1.62 ms per step: GEMV v2 0.72 ms (44%; lm_head ~95 µs, the other
  168 GEMVs ~3.7 µs each), **RoPE 0.41 ms (26%)**, RMSNorm 0.13 ms (8%), attention 0.15 ms (9%), argmax 0.11 ms
  (7%, one block for 152k logits), small elementwise 0.09 ms. GEMV per step: 3.02 ms (step 1) → 0.72 ms.
- Host vs GPU: under the profiler the GPU is busy 73% of the step span (the host needs 2.29 ms per step with NVTX
  ranges, 74 µs per layer for 17 launches). Without NVTX the benchmark (1.73 ms) is within 7% of the kernel time
  (1.62 ms): host and GPU are now balanced, so further kernel savings will soon hit the launch floor.
- Level 6: greedy 589 tok/s; PLD overall 1.94× → 1.13×, `cpp_getters` 0.85× (PLD slower than greedy); identical
  outputs. A 5.3-token verify now costs 3.8× a 1-token forward (step 2: 1.49×): decode got 2.4× faster, while
  multi-token forwards (PLD verify, prefill → TTFT) still run the unchanged Split-K GEMM.
- Note: the profile files captured after this step were named `v1.1-attn_*` but contain the step 3 code
  (`gemv_int4_v2_kernel`); renamed to `v1.1-gemv_*`. There is no separate profile of step 2.

**Open items found by this profile (not in v1.1 scope unless stated):**
1. Multi-token path: a GEMV v2 batched over T ≤ 11 tokens (weights read once) for PLD verify and prefill.
2. RoPE, RMSNorm and argmax cost 0.65 ms of the 1.62 ms of kernels; a precomputed cos/sin table, a single-pass
   RMSNorm and a multi-block argmax should save ~0.4 ms of GPU time.
3. Launch overhead (418 launches per step): CUDA Graphs or the C++ runtime (v2.0, line B).
